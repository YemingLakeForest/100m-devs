## Sequencing note

Phases 0–3 are independent of 4–6 and deliver a visibly different game on their own
(three live backlogs, a readable HUD, a first act that is not a solo grind, and staged
dialogue). Phase 4 must precede Phase 5 because the hero board reuses the upgrade board's
layout and visibility primitives — building them twice is the failure this ordering exists
to prevent.

## Amendment — 2026-08-13, after the handset report (§25.7)

Three layout defects and one design correction came back off a device. The correction reaches
the phases below, so it is recorded here rather than only in the GDD.

**§21.0c — Run 1 carries one idea.** Roles, the three backlogs and the whole upgrade board are
now gated on the first Paradigm Shift, and §11.5's Instant Messenger goes back to §21.6 where
it was. What this changes for the remaining work:

- **Phase 4 (the upgrade board)** is now, by construction, a **Run 2+ screen**. Nothing in the
  board has to answer "what does this look like during Act I", because during Act I there is no
  door. The `?full` fixture added to `App.tsx` is how the board gets looked at.
- **Phase 5 (heroes)** inherits the same gate for free: hero cards are §13.6 and §13.6 is behind
  the shift already.
- **Phase 6 (the story arc)** loses one scene and gains a place to put it. §21.7.2 is Run 2's
  Act 0 rather than Act I's second beat, so the five §21.7.3 hero arrivals now all sit in the
  same run as the tool handovers they are paced against.
- **Phase 3's camera half is unaffected.** Every `DialogueLine` still carries its `focus`; there
  is simply one fewer scene to point a lens at during Run 1.

**And the acceptance gate is now the thing that has to pass.** `npm run check` runs
`scripts/ui-frame.acceptance.mjs`, which checks overlap as well as containment, at five frame
sizes, in the states where the HUD is full. Every phase below adds elements to a rail whose
budget is already spent to the pixel (§10.1a) — the gate is what will say so.
