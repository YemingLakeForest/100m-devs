## What Phase 1 still owes

### 1. §7.8.12's executive suite — the next thing to build

**This is the one substantial gap and it is deliberate.** The suite needs Pixi geometry (glass
walls anchored to `founderDeskPosition()`, one desk per arrived hero, nameplates), a new pick
class threaded through `stage.ts`'s tap pipeline, and §7.8.13's six signature idle behaviours.
Half-building it would leave the room in a worse state than the document — which is the failure
§26.0 exists to prevent.

Everything under it is built and tested: the roster, the levels, the coverage maths, the card
the suite opens, and the placement API (`placeHero` / `recallHero`) the drag will call.

**Until it exists, `hud/Roster.tsx` is doing double duty as the door**, and its module comment
says so. §13.11.2's strip is canon and survives — it answers *"who is idle?"*, which the world
cannot — but §7.8.12 is where a player is meant to reach these people, by looking at them. The
`TEAM` button goes away when the room arrives.

### 2. Placement has an API and no gesture

`placeHero(id, rung, index)` is wired, saved, tested, and drives the whole fold. Nothing calls
it but tests. The gesture is §7.8.9's existing carry, out of the suite onto a unit — so this is
part of item 1 rather than separate from it.

### 3. §13.11.1's coverage is not drawn

*"Coverage is drawn, not stated"* is the load-bearing sentence of §13.6.6 and §13.8, and
`render/heroBadges.ts` already has the footprint maths. Nothing renders it. Also part of item 1.

### 4. Run 2's length has never been measured

§26.1.8's last acceptance item, and §13.12.2 is explicit that if it measures at twenty minutes
the economy moves rather than the table.

### 5. §18's random events are not a system

Found while checking §3.1.6: the only thing in the build that mentions §18 is a Paradigm node
that switches one of its events off. This blocks §3.1.6 item 3 and all of §26.3.3.

## Traps 28–32 — for the register in `HANDOFF.md`

**28. A gate can be weakened by a change that has nothing to do with it.** §21.7.6 hid the three
backlogs behind their heroes, and `?full` — the fixture that exists to be *the worst frame the
HUD ever has to draw* — sets `paradigmShifts` and no milestones. So the worst-case frame quietly
became three readouts emptier than the frame it reproduces, and the rail budget passed for the
wrong reason. That is §25.7.3's fourth hole wearing a new coat. **When a gate changes what it
shows, check the fixture in the same commit.**

**29. Padding a clipping rail is right vertically and wrong horizontally.** `overflow: hidden`
clips to the padding box, so `padding-bottom` gives a button's offset slab room inside the clip.
`padding-inline` does the opposite: the rail's children are already sized to its *content* box,
so horizontal padding narrows that box and pushes them out. Measured at 640×360 with 14px of it,
the offer panel was 230px wide in a 208px content box and hung fourteen pixels off the rail's
left edge — a defect the gate did not have before the padding was added. The sideways overhang
belongs on the one control tall enough to have any.

**30. A give-way rule keyed to width does not fire on a short, wide frame.** §10.1a has a stated
order in which rail content gives way and it was entirely correct; every step of it waited for
`max-height: 400px`. At 898×403 the rail wanted 436px in 381 and *nothing gave way*, because 403
is on the wrong side of 400 by three pixels. Moving the step to 470 — the breakpoint above it,
already in the file — closed 436 → 381 exactly. **Check that a give-way order actually fires at
every frame in the box, not just at the bottom of it.**

**32. A percentage height on a grid item resolves against its grid *area*, and an auto-sized
track containing one is cyclic — so the cap silently does nothing.** `.herotree__frame` asked
for `height: calc(100% - 2 * var(--edge-y))` inside a `display: grid; place-items: center`
host, measured **482 px inside a 436 px box**, with its `BACK` button off the bottom of the
frame. Nothing warns: the declaration is valid, it computes, and the computed value is simply
the content height. A flex item's percentage height resolves against the flex container's
content box instead, which is definite whenever the host is inset to the frame — so both hero
surfaces are `display: flex` and say why in the CSS. **If a height cap on a centred panel
appears to be ignored, look at whether its parent is a grid before you look at the number.**

**31. `{n}{' '}{word}` has the accessible name `"1POINT"`.** `Button` wraps each child in its own
element, so JSX whitespace between two expressions is not in the computed name. It renders
correctly and is unfindable by `getByRole`. Build a label as one template string.
