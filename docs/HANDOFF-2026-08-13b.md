## What is left of it

### 1. The browser gate is red, and it is one problem, not many

`scripts/ui-frame.acceptance.mjs` now asserts that a button's offset slab (the `3px 3px` box-shadow
plus the 4° skew, ~4px outside the border box) is not clipped by any `overflow: hidden` ancestor.
That check is right and it is what caught the "edges lightly cropped" report. It is also exposing
that the two rails have **no slack** — see trap 24 — so the fixes whack-mole: clearing MENU's bottom
slab at 748×336 broke CODE/PARADIGM/UPGRADES at 898×403, and so on.

The honest position: **the check stays, and the rails need a structural answer**, not more
per-button padding. Two real options — pick one, then re-run the gate:

- **Give the rails ~4px of breathing room** (padding inside the rail, on the side its buttons hug),
  so every button's slab has room without a per-button rule. This is the real fix; it costs four
  pixels the handoff says are already spent, so it has to be taken deliberately.
- **Reduce the slab** (`box-shadow: 2px 2px` and/or a 3° skew), so the painted overhang is ~2.5px and
  the existing padding already covers it everywhere.

Until one of those lands, `npm run check` is red.

### 2. Phase 5's two UI components are deliberately not built

`hud/HeroBoard.tsx` and `hud/RosterStrip.tsx` do not exist. That is a decision, not an omission:
hero placement is gated behind **Layer 2 (the Codebase Fork, GP)**, which does not exist yet, and
§13.6.7a's standing rule is that the codebase refuses to ship a tray the player can open onto a board
with nothing reachable on it. Everything under them — the board data, XP, the roster, the coverage
math — is built and tested. When Layer 2 lands, they inherit it for free.

### 3. The MENU placement is unresolved

The user asked for MENU at the left-bottom, and it does not fit: the left rail already carries the
charts, the three backlogs, the speedometer and the velocity readout, and MENU (even UPGRADES-sized)
spills past the rail's clip at the smallest frames. This is the concrete instance of "the readout
rail has no room for a nav control" (trap 26). Revert it to the right rail, or make it a floating
bottom-left control — both are two-line changes.

## Traps 24–27 — for the register in `HANDOFF.md`

**24. A button paints ~4px outside its border box, and the rails clip it.** `box-shadow: 3px 3px 0 0`
and `transform: skewX(-4deg)` together extend ~4px past the border box on the shadow's side. Both
rails are `overflow: hidden` and spent to the pixel, so any button flush against a rail edge loses
those pixels — the "edges lightly cropped" report, verbatim. The lesson that cost the session: **you
cannot fix this one button at a time.** Each clearance patch shifts the overhang to a neighbour or a
neighbouring frame. Reserve the room once, at the rail, or shrink the slab; then let the gate (which
now checks this) hold it.

**25. `justify-items: end` sizes a grid button to `fit-content` = its `max-content`, and it spills
past the track's left edge.** "HIRE 1,000 DEVS NOW" with its cost note was the instance. `max-width:
100%` does *not* rescue it — the track is indefinite so the percentage resolves to auto and is
ignored; the fix is `justify-items: stretch` or an explicit pixel cap (`calc(var(--hud-rail) +
var(--hud-overhang))`). It is trap 20's cousin: the button's own `min-width: 0` is not enough, the
*alignment* is the thing that makes it refuse to wrap.

**26. The readout rail has no room for a nav control.** MENU moved into the left rail overflowed it
at the smallest frames, and the honest repairs (drop the gauge bar, drop the velocity unit line,
shrink the numerals) each fixed one frame and broke another — because they were all trimming the same
over-full column. A control does not belong in a column of *readings*; it belongs in the action rail
or as a floating element. Decide the placement first, then make room once.

**27. The gate's `COMPONENTS`/`PAINTED` allowlists are still hand-maintained, and so is the new
shadow check's scope.** The shadow-clipping check was originally written to run on *every* `.ui-btn`,
which immediately flagged the first-run creator's dice button (a separate, pre-existing 640px
overflow) and turned into another whack-a-mole. It is scoped to `.hud` now. The handoff's warning
about allowlists now has a second face: **a new check that is too broad is as bad as one that is too
narrow** — scope it to the layer you actually meant to protect, in the same commit that adds it.
