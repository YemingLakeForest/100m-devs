## Read this first

Yesterday's handoff said items 3–10 were *"believed to work and covered by tests, which is
precisely the state the two systems at the top of this file were in."* It was right to be
suspicious, and the answer is:

> **Walking eight things a player does found one of them flatly false, one carrying a defect
> nobody had a section for, and a load-bearing comment in the other browser gate that was
> simply untrue. No test in the repo could have seen any of the three.**

The instrument is as much of this session as the fixes are.
**`scripts/playthrough.acceptance.mjs`** plays the game with a mouse. It presses real controls,
taps the real canvas, waits for real triggers to fire off state it produced itself, and asserts
against what is on the screen. **Nothing in it calls a store verb** — that is the whole design,
because §25.9.4's two dead systems both passed every unit test they had, and *a join is
invisible to a test that supplies its own left-hand side.*

| Gate | Owns | Blind to |
|---|---|---|
| `vitest` | Does it compute the right number | Layout and joins — jsdom has no layout engine |
| `ui-frame.acceptance.mjs` | Is it drawn correctly, at five frames | Whether anything leads to the screen it is measuring |
| **`playthrough.acceptance.mjs`** | **Can a player get to it** | Numbers; it asks only whether the door opens |

It is in `npm run check`. That is deliberate and it is expensive — see
[The cost](#the-cost-of-the-new-gate) below, which is a decision the next session may want to
revisit rather than a settled one.

### The one accommodation: `?speed=N`

`render/stage.ts` now runs N whole simulation ticks per frame when the query string asks. Same
family as `?act`, `?devs` and `?full`, and it supplies no left-hand side to anything: N calls at
the frame's own `dt` is arithmetically N frames, so a run walked at speed 40 passes through
every state a run walked at speed 1 does, in the same order. **Repeated whole ticks, never a
bigger `dt`** — payroll, entropy, the tail and §4.12's arrival rates are all integrated per
frame and a fortyfold step would be a different simulation. Clamped at sixty, which is one
simulated minute per wall second.

Without it the walk runs at the pace the game is paced at, three careers over: §21 makes Run 1
four minutes by design and Run 2's climb to the cap is longer again. A gate nobody can afford
to run is a gate that goes stale, which is exactly how items 2a and 11 sat false for weeks.

## What the walk found

### 1. §11's upgrade board was drawn in two coordinate systems — item 4

**The fix is in `UpgradeBoard.tsx`; the write-up is §11.4.1a.**

`NodeView` placed each node at `(node.x + 1.5) · CELL` — the literal padding — while the
connector layer placed each line endpoint at `(node.x + pad − bounds.minX) · CELL`. Those agree
for a board whose furthest cell is `(0,0)` and for no other. §11's board runs three cells west
of Instant Messenger and three north, so **every node was drawn three cells up and left of the
line drawn to reach it**, and `B3`, `B4`, `C2` and `C2a` landed at *negative* coordinates —
outside the world box, behind the scroller's clip, at no scroll position.

Half of §11.2's protocol chain and half of §11.3's culture chain could be seen on a connector
and never bought. The board also opened at scroll `(0,0)`, the empty corner, because the
centring effect `HeroTree.tsx` has carried since the day it was written was never written here.

**Why nothing saw it.** jsdom does no layout; the browser gate measures containment and a node
clipped to nothing is contained; and the one test that came near — *"grows outward from Instant
Messenger in all four directions"* — compares the nodes **with each other**, so translating the
whole node layer leaves it green. Two tests were added that assert the *join*: every node's
centre is a connector endpoint, and every node is inside the world it declares.

### 2. The founder's own board is behind a camera that has moved on — item 9

**Not fixed. Written up as §13.7.1a and on the blocked-on-a-human list.**

§13.6.6 forbids a management screen so the door to §13.7.1's tree is a person: tap your own
avatar. Measured at 997x448 — the largest frame in §23.4.2's box — with the camera where a
fresh load leaves it, the founder's avatar is on screen at 8 developers and at **no headcount
above it**. §7.8.10 pins the corner workstation to a fixed point and the room grows away from
it.

It is not a dead control and the note says so precisely: a drag brings the corner back, and a
player who has poked themselves is already parked there — in the career the walk played, the
founder was still tappable at 107 developers with no drag at all. What has gone is the
*guarantee*: §4.5d's corner shortcut, the one control that walks the lens back on demand, is
`display: none` under `max-height: 470px` and **every frame the game supports is 470 px or
shorter**.

Restoring it was tried and refused by the rail: at 640x360 the wrap absorbs the slab and then
clips §10.1's UPGRADES by four pixels. §10.1a says both rails are full. The fix that costs no
pixels is a camera bias, and that is a composition decision.

### 3. A comment in the browser gate said a wire was not connected, and it was

`ui-frame.acceptance.mjs` carried *"nothing loads the save at boot today, so this is insurance
rather than a fix"*. `store.ts` calls `initPersistence()` **at module scope** and has for as
long as that function has existed — the save is read before the first render, by design. So the
`localStorage.removeItem` that comment excused as insurance is the only thing keeping the gate
testing Run 1 at all.

It cost this session an hour: the walk was built on the comment, and two of its three careers
were wrong until the walk's own results made no sense. Corrected in place.

## Traps 38–44 — for the register in `HANDOFF.md`

**38. When one picture is built from two coordinate systems, the test is that they agree.**
§11's board drew its nodes from the padding and its connectors from the bounds, and the two
matched only for a tree whose furthest cell is the origin. The test that came nearest compared
the nodes **with each other** — *"grows outward in all four directions"* — and a set compared
to itself cannot see the set being in the wrong place. The assertion that works is the join: a
node's centre is a connector endpoint.

**39. A control removed because "another door exists" needs that door checked at every scale.**
§4.5d's corner shortcut was hidden on the argument that tapping your own avatar does the same
thing. It does — at eight developers. The room grows away from a fixed corner and the resting
frame loses it, so the argument expired without anybody noticing, on every device, because the
media query that hid it covers the whole of §23.4.2's box. **Trap 37 with the tense changed:
that one is a deferral comment that outlived the deferral; this is a justification that
outlived its conditions.**

**40. A harness that aims at a fixed screen point is aiming at a camera that has moved.** The
walk tapped the founder's desk fifty times and landed seven, because the first tap calls
`focusFounderCamera` and the lens walks the target away from the pointer. Act I never ended;
the run sat in `act1_poke` with four games shipped and fifty thousand dollars in the bank,
which is a perfectly reasonable studio and not the one the script is about. **Every canvas
sweep in the walk re-finds rather than remembers.**

**41. `affordable` is `cash >= cost`, with no payroll buffer — so a harness that presses HIRE
whenever it is live will bankrupt Run 2.** It did, twice, at about eleven hundred developers on
a cap of a hundred. That is §6's lesson working exactly as designed and it is not a bug; what
it means is that a walk has to *play*, not just press. The walk now reads the two numbers a
player reads — the NET line under CASH, and the speedometer at 50% for the cap — and stops.

**42. A note saying a wire is not connected is worth checking before you build on it.**
`ui-frame.acceptance.mjs` said nothing loaded the save at boot. `store.ts` has called
`initPersistence()` at module scope for as long as that function has existed. Two of the walk's
three careers were designed around the comment and none of the results made sense until
somebody read the store instead. The note is corrected in place — and the line it described as
"insurance" turns out to be the only thing keeping that gate testing Run 1.

**43. You cannot clear the save and reload — §24.9's unload handler writes it straight back.**
`installAutoSave` saves on `pagehide`, so `removeItem` then `reload()` deletes a career and the
reload's own unload restores it from the state still in memory. The walk needed three careers
and got the same one three times, reporting a Run 1 that had already prestiged. **A career
cannot be ended from inside the page that is living it**; the fix is a fresh browser context.
The behaviour is correct — it is §24.9 doing exactly what it promises — and it is the kind of
correct that will cost somebody an hour again.

**44. A panel that is leaving still has its buttons, and `.first()` will find them.** §10.8's
panels stay mounted through their exit so there is something to animate, so for a few hundred
milliseconds `getByRole('button', …)` matches the dying copy as well as the live one. Every
click then lands on a pane on its way out. That is not the trap; **the trap is what it looks
like** — the walk's twenty taps on THE THREAD all missed, the loop ran to its cap, and the
assertion underneath it (*"and then it comes back"*) passed by describing an event nobody had
touched.

**The same loop then missed for a second, different reason** once that was fixed: §18.0a's
scene was still playing over the card, and §10.7a.3's scrim owns every tap while it is. Two
independent ways for a press to silently not happen, one after the other, in ten lines.

> **A loop that presses something must assert that the pressing worked**, not that it finished.
> The fix is three lines: scope live surfaces with `[data-phase="in"]`, play out whatever the
> game is saying before pressing, and **fail loudly** if the thing is still there after the
> number of presses the design says it costs. The third one is what caught the second bug — a
> vacuous pass is worse than a failure, because it is a failure that recruits everything below
> it as evidence.

## The cost of the new gate

`npm run check` was about five minutes and is now about twenty. The walk plays three careers in
a real Chrome, and Run 2's growth to the cap is most of it even compressed forty-fold.

It is in `check` on `ui-frame.acceptance.mjs`'s own argument — reason 2 in its header is that a
gate outside `check` is not a gate — and the counter-argument is real: a check nobody runs
because it takes twenty minutes fails the same way. **If it is carved out, carve it out on
purpose and put it somewhere that runs**, rather than letting it become the script this project
has already been burned by twice.

`WALK_SPEED` and `WALK_LEG_MS` are environment overrides if the machine is slower than this one.
